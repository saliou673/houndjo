# Backlog agent-ready — SaaS écoles coraniques

Backlog détaillé pour développement autonome par agents IA. Chaque ticket porte assez de détail (schéma SQL, signatures d'endpoints, DTO champ par champ, packages, cas de test avec assertions, composants front) pour être codé et testé sans contexte externe.

**Base :** starter `spring-next-saas-starter` (Spring Boot 4 / Java 25 hexagonal, Next.js 16 web, Expo/React Native mobile, client Kubb). Placeholder à renommer : `houndjo` → nom projet ; package `com.houndjo`.

## 0. Contrat de conventions (à respecter dans TOUS les tickets)

### Backend — structure hexagonale par agrégat

Chaque nouvel agrégat `X` crée exactement ces fichiers :

```
houndjo-core/.../domain/models/<ctx>/X.java              # agrégat (extends Auditable<Long>)
houndjo-core/.../domain/models/<ctx>/XFilter.java         # si listable/filtrable
houndjo-core/.../domain/ports/in/XUseCase.java            # port entrant (use case)
houndjo-core/.../domain/ports/out/persistenceport/XPersistencePort.java
houndjo-core/.../domain/exceptions/XNotFoundException.java (+ autres au besoin)
houndjo-app/.../application/<ctx>/XService.java           # implémente XUseCase, dépend des ports out
houndjo-app/.../infrastructure/adapter/out/persistence/<ctx>/XEntity.java
houndjo-app/.../infrastructure/adapter/out/persistence/<ctx>/XMapper.java       # domain<->entity
houndjo-app/.../infrastructure/adapter/out/persistence/<ctx>/XRepository.java   # Spring Data JPA
houndjo-app/.../infrastructure/adapter/out/persistence/<ctx>/XPersistenceAdapter.java # implémente port out
houndjo-app/.../infrastructure/adapter/in/rest/controller/<ctx>/XController.java
houndjo-app/.../infrastructure/adapter/in/rest/controller/dto/<ctx>/*.java      # requêtes/réponses + mappers DTO
houndjo-app/src/main/resources/db/changelog/ddl/NNNNN-x-create-table.sql
houndjo-tests/.../<ctx>/XControllerIT.java                # Testcontainers
```

**Règles domaine :**
- Agrégats étendent `Auditable<Long>` (fournit `id`, `creationDate`, `lastUpdateDate`, `lastUpdatedBy`). Ne pas redéclarer ces champs.
- Constructeur privé + fabriques statiques `create(...)` (nouvel objet) et `rehydrate(...)` (reconstruction depuis persistence). Cf. `User`, `RoleGroup`.
- Zéro dépendance framework dans `houndjo-core`. `Objects.requireNonNull` pour les invariants.
- Value objects immuables (records) quand pertinent (cf. `Email`, `UserInfo`).

**Règles persistence adapter :** envelopper chaque opération dans `AdapterPersistenceUtils.executeDbOperation(() -> ..., "message d'erreur")`. Annoter l'adapter `@Service @Transactional @RequiredArgsConstructor`. Cf. `AppConfigurationPersistenceAdapter`.

**Règles controller :**
- `@RestController @Validated @RequiredArgsConstructor @Tag(name="...")`.
- `@RequestMapping(path="/api/v1/<resource-kebab>", version="1.0")` (versionnement par header `X-API-Version`).
- `@PreAuthorize("hasAuthority('<resource>:<action>')")` au niveau classe et/ou méthode.
- Création → `@ResponseStatus(HttpStatus.CREATED)` ; suppression → `NO_CONTENT`.
- Listes paginées → retour `PaginatedResult<XDTO>` avec `@PageableDefault(size=DEFAULT_PAGE_SIZE_INT, sort="creationDate", direction=DESC)`.
- Jamais d'entité JPA ni de modèle domaine exposé : toujours des DTO + mapper DTO.
- Requêtes validées avec `@Valid @RequestBody`, contraintes Jakarta (`@NotBlank`, `@NotNull`, `@Size`, `@Email`, `@Positive`…).

**Règles migration Liquibase :**
- En-tête `--liquibase formatted sql` puis `--changeset houndjo:NNNNN-nom`.
- `BIGINT GENERATED BY DEFAULT AS IDENTITY` pour les PK, `TIMESTAMP NOT NULL DEFAULT now()` pour les dates d'audit, `last_updated_by VARCHAR(255) NOT NULL DEFAULT 'system'`.
- Contraintes nommées : `pk_<table>`, `uq_<table>_<col>`, `fk_<table>_<ref>`. FK avec `ON DELETE` explicite.
- Ajouter l'include dans `ddl/master.yml` (et `dml/master.yml` pour les seeds). Numéroter à la suite de l'existant (le starter va jusqu'à `00009`).
- Index sur toute colonne de filtrage fréquent, **notamment `organization_id`**.
- **Nommage des colonnes** : les champs domaine sont en `camelCase`, les colonnes SQL en `snake_case`, le mapping est assuré par le `Mapper`. Règle de conversion systématique : `organizationId`→`organization_id`, `amountPerSession`→`amount_per_session`, `sessionsPerWeek`→`sessions_per_week`, `teacherUserId`→`teacher_user_id`, `birthDate`→`birth_date`, `guardianName`→`guardian_name`, `guardianPhone`→`guardian_phone`, `dueDate`→`due_date`, `amountDue`→`amount_due`, `amountPaid`→`amount_paid`, `paidOn`→`paid_on`, `startDate`→`start_date`, `endDate`→`end_date`, `startTime`→`start_time`, `endTime`→`end_time`, `displayOrder`→`display_order`, `errorCount`→`error_count`, `currencyCode`→`currency_code`, `invitationCode`→`invitation_code`, `expiresAt`→`expires_at`. Aucune colonne ne doit rester en camelCase.

**Règles i18n backend :** aucun message en dur. Clés dans `messages_fr.properties` / `messages_en.properties` (+ `messages_ar.properties` créé, vide ou traduit selon version). Exceptions résolues via `MessageSource`.

### Frontend web — Next.js

- Un dossier `features/<feature>/` (logique) + routes sous `app/`. Cf. `features/users`, `features/role-groups`.
- **Aucun appel HTTP manuel** : régénérer le client via Kubb (`pnpm --filter @houndjo/apiclient generate` ou équivalent) après tout changement d'OpenAPI, puis consommer les hooks TanStack Query générés.
- Formulaires : React Hook Form + Zod. Tables : TanStack Table (réutiliser le `DataTable` existant). État global léger : Zustand.
- i18n : `next-intl`, clés dans `src/messages/{fr,en}.json`. Aucune chaîne en dur.
- **Responsive obligatoire** : breakpoints Tailwind `sm/md/lg`. Tables → cartes empilées sur mobile ; actions accessibles au pouce.
- **RTL-ready** : propriétés logiques (`ms-*`/`me-*`/`ps-*`/`pe-*`, `text-start`/`text-end`) au lieu de `ml/mr/pl/pr/text-left/right`.

### Frontend mobile — Expo + BNA UI

- **BNA UI** (ui.ahmedbna.com) : lib copy-source (comme shadcn), composants copiés dans le projet, imports via `@/components/ui/*`, `@/components/charts/*`, `@/hooks/*`, `@/theme/*`.
- **React Native pur** : `StyleSheet` + prop `style`, **jamais `className`**, pas de Tailwind, pas de DOM.
- Couleurs via le hook `useColor` — **jamais de hex en dur**. Tailles via tokens `HEIGHT`, `FONT_SIZE`, `BORDER_RADIUS`, `CORNERS` depuis `@/theme/globals`.
- Providers : `ThemeProvider` + `ModeProvider` (clair/sombre), à réconcilier avec le système d'apparence existant de l'app.
- Même client Kubb partagé que le web.

### Definition of Done (tout ticket)

1. Code conforme aux conventions ci-dessus.
2. Tests : back → test d'intégration Testcontainers couvrant nominal + erreurs + **isolation tenant** ; front → au minimum le happy path se compile et rend sans erreur.
3. i18n : clés FR présentes (EN/AR selon version), zéro chaîne en dur.
4. Migration Liquibase appliquée et réversible ; OpenAPI régénéré ; client Kubb régénéré.
5. Web responsive vérifié ; mobile rendu iOS + Android.
6. `@PreAuthorize` posé et permission seedée en DML.

# ÉPIC E0 — Fondations multi-tenant

### TICKET E0-1 — ADR & socle d'isolation multi-tenant
**Type :** Tech / ADR + Domaine · **Dépend de :** —
**Description :** Décision : **discriminant par colonne `organization_id`** sur chaque table métier (recommandé MVP). Implémenter la résolution du tenant courant et le filtrage systématique.
**Livrables :**
- ADR sous `docs/architecture/adr-001-multitenancy.md`.
- `TenantContext` (composant applicatif, package `com.houndjo.application.tenant`) exposant `Optional<Long> currentOrganizationId()`, alimenté depuis le contexte de sécurité (l'organisation active est portée par un claim JWT ou résolue via le Membership actif — cf. E0-2).
- Convention : tout use case métier reçoit/vérifie l'`organizationId` ; tout `PersistencePort` de liste prend `organizationId` en paramètre et tout `Repository` filtre dessus.
- (Option retenue à documenter) filtre Hibernate `@FilterDef(name="orgFilter")` activé par intercepteur, OU garde applicative explicite. Choisir la garde applicative explicite pour le MVP (plus simple à tester, pas de magie).
**Critères d'acceptation :**
- `TenantContext` résout l'org courante d'une requête authentifiée ; lève `MissingTenantException` (HTTP 400) si absente sur une route métier.
- Documentation de la convention dans l'ADR.
**Tests (`houndjo-tests`) :**
- `given` deux orgs A et B avec chacune une donnée métier de test, `when` un user de A liste, `then` il ne voit que les données de A (assertion sur taille + IDs).
- `when` requête métier sans org active `then` HTTP 400 code i18n `error.tenant.missing`.

### TICKET E0-2 — Membership : rôle scopé organisation
**Type :** Domaine + API · **Dépend de :** E0-1
**Description :** Agrégat `Membership` liant User × Organisation × rôle d'organisation. Les rôles plateforme (Sysadmin) restent gérés par le RBAC global existant ; les rôles métier sont portés par le Membership.
**Modèle domaine :** `Membership extends Auditable<Long>` : `Long userId`, `Long organizationId`, `OrganizationRole role`, `MembershipStatus status` (`ACTIVE`, `INVITED`, `REVOKED`). Enum `OrganizationRole` : `SCHOOL_OWNER`, `SCHOOL_ADMIN`, `TEACHER` (extensible : `PARENT`, `STUDENT` en V1). Fabriques `create(userId, organizationId, role)`, `rehydrate(...)`. Méthodes `revoke()`, `changeRole(newRole)`, `activate()`.
**Persistence / DDL `00010-membership-create-table.sql` :**
```sql
--liquibase formatted sql
--changeset houndjo:00010-membership-create-table
CREATE TABLE IF NOT EXISTS membership (
    id               BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    user_id          BIGINT       NOT NULL REFERENCES app_user (id) ON DELETE CASCADE,
    organization_id  BIGINT       NOT NULL REFERENCES organization (id) ON DELETE CASCADE,
    role             VARCHAR(30)  NOT NULL,
    status           VARCHAR(20)  NOT NULL,
    creation_date    TIMESTAMP    NOT NULL DEFAULT now(),
    last_update_date TIMESTAMP    NOT NULL DEFAULT now(),
    last_updated_by  VARCHAR(255) NOT NULL DEFAULT 'system',
    CONSTRAINT pk_membership PRIMARY KEY (id),
    CONSTRAINT uq_membership_user_org UNIQUE (user_id, organization_id),
    CONSTRAINT fk_membership_user FOREIGN KEY (user_id) REFERENCES app_user (id),
    CONSTRAINT fk_membership_org FOREIGN KEY (organization_id) REFERENCES organization (id)
);
CREATE INDEX idx_membership_org ON membership (organization_id);
CREATE INDEX idx_membership_user ON membership (user_id);
```
(Note : dépend de la table `organization` d'E1-1 — ordonnancer le changeset après.)
**Sécurité :** étendre la résolution des autorités pour que `@PreAuthorize` puisse tester un rôle **dans l'org active**. Ajouter une méthode SpEL exposée (ex. `@authz.hasOrgRole('TEACHER')`) via un bean `authz` qui lit `TenantContext` + Memberships de l'utilisateur.
**API — `MembershipController` `/api/v1/organizations/{orgId}/memberships` :**
- `GET` (paginé) → `PaginatedResult<MembershipDTO>` — perm `membership:read`.
- `PATCH /{id}/role` body `{ "role": "TEACHER" }` → `MembershipDTO` — perm `membership:update`.
- `DELETE /{id}` (révoque) → 204 — perm `membership:delete`.
- `MembershipDTO` : `{ id, userId, userEmail, userFullName, organizationId, role, status, creationDate }`.
**DML permissions :** seeder `membership:read/create/update/delete` et les assigner aux groupes/rôles pertinents.
**Critères d'acceptation :**
- Un User peut avoir des Memberships dans plusieurs orgs avec des rôles différents.
- `@authz.hasOrgRole(...)` renvoie vrai/faux selon l'org active.
- Contrainte d'unicité (un seul Membership par couple user/org) respectée.
**Tests :**
- création de Memberships dans 2 orgs pour le même user → rôles distincts résolus correctement.
- un `TEACHER` de l'org A n'a pas les droits `SCHOOL_ADMIN` sur l'org A ni aucun droit sur l'org B (assertions 403).
- changement de rôle et révocation reflétés dans les autorités.

# ÉPIC E1 — Organisation & gestion des membres

### TICKET E1-1 — Agrégat Organization & inscription d'une école
**Type :** Domaine + API · **Dépend de :** E0-1
**Modèle domaine** (`domain/models/organization/Organization.java`, `extends Auditable<Long>`) :
`String name`, `String slug` (unique, kebab, dérivé du nom), `String contactEmail`, `String phoneNumber` (nullable), `String address` (nullable), `String defaultCurrencyCode` (réfère `CURRENCY` d'AppConfiguration, défaut `GNF`), `String defaultLanguageKey` (défaut `fr`), `String timezone` (défaut `Africa/Conakry`), `OrganizationStatus status` (`ACTIVE`, `SUSPENDED`). Fabriques `create(name, contactEmail, ...)` (génère slug, statut `ACTIVE`), `rehydrate(...)`. Méthode `updateProfile(...)`.
**DDL `00009b-organization-create-table.sql`** (à ordonner **avant** membership) :
```sql
--liquibase formatted sql
--changeset houndjo:00009b-organization-create-table
CREATE TABLE IF NOT EXISTS organization (
    id                    BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    name                  VARCHAR(150) NOT NULL,
    slug                  VARCHAR(160) NOT NULL,
    contact_email         VARCHAR(255) NOT NULL,
    phone_number          VARCHAR(20),
    address               VARCHAR(255),
    default_currency_code VARCHAR(10)  NOT NULL DEFAULT 'GNF',
    default_language_key  VARCHAR(5)   NOT NULL DEFAULT 'fr',
    timezone              VARCHAR(64)  NOT NULL DEFAULT 'Africa/Conakry',
    status                VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    creation_date         TIMESTAMP    NOT NULL DEFAULT now(),
    last_update_date      TIMESTAMP    NOT NULL DEFAULT now(),
    last_updated_by       VARCHAR(255) NOT NULL DEFAULT 'system',
    CONSTRAINT pk_organization PRIMARY KEY (id),
    CONSTRAINT uq_organization_slug UNIQUE (slug)
);
```
**Use case `OrganizationUseCase` :** `Organization registerSchool(RegisterSchoolCommand cmd, Long creatorUserId)` — crée l'organisation **et** un Membership `SCHOOL_OWNER ACTIVE` pour le créateur, dans **une seule transaction** (dépend de E0-2 pour le Membership ; si E0-2 pas encore mergé, créer l'org seule et compléter ensuite). `Organization getById(Long id)`, `List<Organization> getMyOrganizations(Long userId)`, `Organization updateProfile(Long id, UpdateOrgCommand cmd)`.
**API `OrganizationController` `/api/v1/organizations` :**
- `POST` body `RegisterSchoolRequest { @NotBlank name, @Email contactEmail, phoneNumber?, address?, defaultCurrencyCode?, defaultLanguageKey? }` → 201 `OrganizationDTO` — auth : tout user connecté.
- `GET /mine` → `List<OrganizationDTO>` (orgs du user courant) — auth connecté.
- `GET /{id}` → `OrganizationDTO` — perm `organization:read` **dans l'org**.
- `PUT /{id}` body `UpdateOrganizationRequest` → `OrganizationDTO` — `@authz.hasOrgRole('SCHOOL_OWNER','SCHOOL_ADMIN')`.
- `OrganizationDTO` : `{ id, name, slug, contactEmail, phoneNumber, address, defaultCurrencyCode, defaultLanguageKey, timezone, status, creationDate }`.
**Critères d'acceptation :** un user peut créer plusieurs écoles ; à la création il devient owner ; slug unique auto-généré (collision → suffixe numérique).
**Tests :** register → 201 + Membership owner créé ; `GET /mine` renvoie les orgs du user et pas celles des autres ; update par un non-membre → 403 ; slug en collision → suffixé.

### TICKET E1-2 — Invitation de profs/admins (scopée organisation)
**Type :** Domaine + API · **Dépend de :** E1-1, E0-2
**Description :** Étendre le mécanisme d'invitation **existant** du starter (`AccountUseCase.createManagedUser` + `completeInvitation(code, password)`) pour porter une **cible organisation + rôle**. Ne pas réécrire le flux de code/expiration : le réutiliser.
**Modèle :** `OrganizationInvitation extends Auditable<Long>` : `Long organizationId`, `Email email`, `OrganizationRole role`, `String invitationCode` (réutilise la génération existante), `Instant expiresAt`, `InvitationStatus status` (`PENDING`, `ACCEPTED`, `REVOKED`, `EXPIRED`). L'invitation **cible un email, pas un userId**.
**DDL `00011-organization-invitation-create-table.sql`** — colonnes : `id BIGINT GENERATED BY DEFAULT AS IDENTITY`, `organization_id BIGINT NOT NULL`, `email VARCHAR(255) NOT NULL`, `role VARCHAR(30) NOT NULL`, `invitation_code TEXT NOT NULL`, `expires_at TIMESTAMP NOT NULL`, `status VARCHAR(15) NOT NULL`, + audit standard. Contraintes : `pk_organization_invitation`, `fk_org_invitation_org FOREIGN KEY (organization_id) REFERENCES organization(id) ON DELETE CASCADE`, `uq_org_invitation_code UNIQUE (invitation_code)`. Index : `idx_org_invitation_org (organization_id)`.

# ÉPIC E2 — Référentiel Coran (parallélisable)

### TICKET E2-1 — Modèle & seed du référentiel Coran
**Type :** Domaine + données · **Dépend de :** —
**Description :** Données de référence **immuables et globales** (pas de `organization_id`). Structure permettant les conversions verset ↔ page ↔ juz ↔ hizb.
**Tables (DDL `00012-quran-reference-create-table.sql`) :**
```sql
--liquibase formatted sql
--changeset houndjo:00012-quran-reference-create-table
CREATE TABLE IF NOT EXISTS quran_surah (
    number            SMALLINT     NOT NULL,   -- 1..114
    name_arabic       VARCHAR(80)  NOT NULL,
    name_transliteration VARCHAR(80) NOT NULL,
    name_fr           VARCHAR(80)  NOT NULL,
    name_en           VARCHAR(80)  NOT NULL,
    revelation_place  VARCHAR(10)  NOT NULL,   -- MECCAN / MEDINAN
    verse_count       SMALLINT     NOT NULL,
    CONSTRAINT pk_quran_surah PRIMARY KEY (number)
);
CREATE TABLE IF NOT EXISTS quran_verse (
    id            BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    surah_number  SMALLINT  NOT NULL REFERENCES quran_surah (number),
    verse_number  SMALLINT  NOT NULL,          -- ayah within surah
    page          SMALLINT  NOT NULL,          -- 1..604 (Mushaf Medine)
    juz           SMALLINT  NOT NULL,          -- 1..30
    hizb          SMALLINT  NOT NULL,          -- 1..60
    hizb_quarter  SMALLINT  NOT NULL,          -- 1..240 (rub' al-hizb)
    CONSTRAINT pk_quran_verse PRIMARY KEY (id),
    CONSTRAINT uq_quran_verse UNIQUE (surah_number, verse_number)
);
CREATE INDEX idx_quran_verse_page ON quran_verse (page);
CREATE INDEX idx_quran_verse_juz  ON quran_verse (juz);
CREATE INDEX idx_quran_verse_hizb ON quran_verse (hizb);
```
**Seed (DML) :** insérer les 114 sourates (noms ar/translit/fr/en, lieu, nombre de versets) et les 6236 versets avec leur mapping page/juz/hizb/quarter. **Source :** générer le DML à partir d'un jeu de données Coran de référence libre (ex. données Tanzil/QUL de mapping ayah→page pour le Mushaf Medine 604 pages). Le ticket inclut un script de génération reproductible (`scripts/generate-quran-seed.*`) qui produit le fichier DML.
**Value objects domaine :** `Surah`, `Verse`, `QuranPortion` (représente une plage : `fromSurah/fromVerse` → `toSurah/toVerse`, avec dérivés page/juz/hizb). Port `QuranReferencePort` : `getSurah(n)`, `versesOfSurah(n)`, `portionForPageRange(from,to)`, `portionForJuz(n)`, `versesBetween(fromRef, toRef)`, `pageOf(surah, verse)`.
**Critères d'acceptation :**
- Comptes exacts : `count(surah)=114`, `count(verse)=6236`, `max(page)=604`, `max(juz)=30`, `max(hizb)=60`.
- Conversions testées : page 50 → plage (surah/verset) correcte ; juz 5 → plage de pages correcte ; verset (2:255) → page connue.
**Tests :** assertions de comptes ; 3+ conversions vérifiées contre des valeurs de référence connues ; intégrité (chaque sourate a exactement `verse_count` versets).
